# FSTEC Monitor

Монитор версий документов раздела `fstec.ru/dokumenty/vse-dokumenty`. Отдельно архивирует исходный HTML, нормализованный HTML-текст, PDF/ODT и извлечённый текст вложений. Различает бинарную замену файла и содержательное изменение.

## Возможности

- рекурсивный обход категорий и пагинации;
- неизменяемое content-addressed хранилище по SHA-256;
- SQLite для одиночной установки или PostgreSQL в Docker Compose;
- HTML raw/structural/semantic hashes;
- PDF и ODT binary/semantic hashes;
- события: новый/удалённый документ или файл, изменение HTML, бинарная либо содержательная замена вложения;
- Telegram-уведомления;
- Telegram-управление: `/status`, `/changes`, `/report ID`, `/errors`, `/scan`;
- отчёты с кратким резюме, подробным unified diff и old/new версиями файлов;
- жёсткая квота архива 5 ГиБ: история не удаляется, при переполнении новая загрузка фиксируется как ошибка;
- игнорирование категорий через `FSTEC_IGNORED_CATEGORIES` без удаления уже сохранённой истории;
- заявки пользователей на доступ с подтверждением администратором в Telegram;
- повторные попытки, backoff и малая нагрузка на сайт;
- ускоренная синхронизация: граф зависимостей «каталог → документ → вложения», conditional GET по `ETag`/`Last-Modified`, bounded concurrency;
- автоматическая проверка раз в сутки в 12:00 по локальному времени сервера;
- настраиваемое расписание и ручной запуск через Telegram.

## Быстрый запуск без Docker

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -e '.[dev]'
cp .env.example .env
fstec-monitor init
fstec-monitor baseline
fstec-monitor run
```

Первый полный проход выполняйте именно через `baseline`: он сохраняет текущие версии без рассылки ложных событий.

## Docker Compose

```bash
cp .env.example .env
# Замените пароль PostgreSQL одновременно в docker-compose.yml и DATABASE_URL.
docker compose build
docker compose run --rm monitor fstec-monitor baseline
docker compose run --rm monitor fstec-monitor run
```

## Telegram

Заполните в `.env`:

```dotenv
FSTEC_TELEGRAM_BOT_TOKEN=123456:token
FSTEC_TELEGRAM_CHAT_ID=123456789
FSTEC_STORAGE_QUOTA_BYTES=5368709120
FSTEC_MAX_CONCURRENCY=8
FSTEC_ATTACHMENT_AUDIT_INTERVAL_SECONDS=86400
FSTEC_IGNORED_CATEGORIES=Информационные и аналитические материалы
```

После первого прохода повторная проверка не скачивает заново неизменившиеся
страницы: серверу отправляются валидаторы, а ответ `304 Not Modified` не создаёт
новую версию. Вложения являются зависимыми узлами графа: они проверяются при
изменении страницы документа и отдельным глубоким аудитом раз в сутки. Число
одновременных документов ограничено `FSTEC_MAX_CONCURRENCY`.

После запуска администратор может использовать:

При `/start` бот автоматически показывает постоянную клавиатуру быстрых действий,
а кнопка `☰` Telegram содержит тот же список команд.

- `/status` — количество документов и вложений, даты последней проверки и изменения, статус изменений, квота и ошибки;
- `/changes 10` — последние содержательные события;
- `/report 123` (или `/diff 123`) — всегда прикладывает файл `diff_123.md` с полным отчётом и unified diff «до/после», плюс старую/новую версию файла, если она помещается в лимит Telegram;
- `/errors` — последние ошибки загрузки и хранения;
- `/clear_errors` — очистка журнала ошибок (`fetch_error`, `storage_error`) с подтверждением; история документов и diff'ы не затрагивается;
- `/users` — заявки пользователей на доступ и кнопки «разрешить/отклонить»;
- `/ignore` — список игнорируемых категорий и inline-кнопки для включения/выключения игнора по каждой известной категории (сохраняется в БД, действует вместе с `FSTEC_IGNORED_CATEGORIES`);
- `/settings` — выбрать расписание: раз в сутки в 12:00, раз в сутки в 00:00,
  каждые 2 часа или выключить автозапуск;
- `/scan` — запустить проверку вручную. Новые документы и изменения приходят автоматически.

Для экономии ресурсов включайте только один автоматический запуск: либо Telegram-бот
с его внутренним расписанием, либо `fstec-monitor.timer`. Если включены оба режима,
они могут одновременно начать одну и ту же проверку в 12:00.

При неизменившемся ответе серверу отправляются `ETag`/`Last-Modified`, а ответ
`304 Not Modified` не создаёт новую версию и не записывает объект на диск. Новые
объекты имеют content-addressed имена: повторная запись одинаковых HTML/PDF/ODT
не перезаписывает файл. Содержательные версии сохраняются для аудита; поэтому
суточный интервал ограничивает количество сетевых запросов и SQLite-операций, но
не удаляет историю.

HTML-уведомления и уведомления о вложениях содержат прямую ссылку на страницу
документа. Повторяющиеся markup-only HTML-снимки не архивируются, чтобы не
заполнять SSD; содержательные изменения и версии PDF/ODT сохраняются.

## systemd

Рекомендуемые пути:

- код: `/opt/fstec-monitor`;
- venv: `/opt/fstec-monitor/.venv`;
- env: `/etc/fstec-monitor.env`;
- данные: `/var/lib/fstec-monitor`.

В env укажите:

```dotenv
FSTEC_DATABASE_URL=sqlite:////var/lib/fstec-monitor/fstec-monitor.db
FSTEC_STORAGE_DIR=/var/lib/fstec-monitor/objects
```

Затем скопируйте unit-файлы из `systemd/`, выполните `systemctl daemon-reload` и `systemctl enable --now fstec-monitor.timer`.

## Важные свойства

Старые объекты никогда не перезаписываются. Ошибка HTTP не считается удалением. Изменение счётчиков скачивания не должно влиять на semantic hash, однако исходный HTML сохраняется для аудита. Парсер специально написан эвристически: при изменении шаблона сайта исходные снимки позволят повторно обработать архив.
